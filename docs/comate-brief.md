# The Comate adaptation

## At a glance

**What ships**

The byte identical copy of the canonical skill at
`.comate/skills/recognitio/`, this brief, and the gate at
`scripts/check_comate.py`. No Comate manifest, package, or
plugin file ships, because none is evidenced.

**What was proven**

The implementer record places the skill format and both
project paths and the user path. The official Linux client
at version 3.11.5 downloaded from Baidu's own installer
record with its published hash matching, installed on this
box, and opened in an empty window and reached its agent start page. The editor command line in the client
bundle reports the same version.

**What is unverified**

Everything past the sign in the agent
surface demands. Invocation inside a live Comate
session stays unverified, and the frontmatter tolerance,
the bundled script execution, the size limit, and the
precedence questions stand open in the rules below.

community skill folder format and the canonical skill

names. What ships is the copy on the native project path,
this brief, and the gate that pins both. The contract lives
in the Comate rules section below, and the gate at
scripts/check_comate.py pins it.

## The second packet guard

Every rule below carries a derivation note naming the
canonical skill section it restates or the primary or
implementer citation it reports, pinned by the gate at
`scripts/check_comate.py`, so the scoped guidance cannot
become a rival instruction source. A rule with neither is a
rival instruction source and fails the build.

## The Comate rules

### C1. The format is a named folder holding SKILL.md

A Comate skill is a folder named for the skill holding a
SKILL.md file. No manifest file, package file, or
registration step is evidenced for the folder itself at
either scope, so this build ships none. The two implementer
records write plain SKILL.md folders for Comate and name no
Comate specific wrapper, and the announcement tier claims
compatibility with the community Skill protocol whose
required fields are name and description.

Derives from the Personal KB marketplace page at
marketplace.visualstudio.com, item Rebekah.personal-kb, and
the Microi marketplace page, item Microi.v8-engine, both
read in full on 2026-10-30, and the 4.0 announcement at
comate.baidu.com/zh/news/news/36 at the tier the summary
states.

### C2. The canonical folder already stands on one project path

The project scope record names two paths together, the
canonical `.agents/skills/recognitio/` and the native
`.comate/skills/recognitio/`, with project skills auto
discovered on the same record. The canonical skill
therefore needs no move and no conversion for Comate.
Whether a given client reads both paths, or different
client versions read different ones, is not stated in the
record and stays unverified.

Derives from the Microi marketplace page at
marketplace.visualstudio.com, item Microi.v8-engine, read
in full on 2026-10-30, whose per host table states that it
follows each host's official protocol and lists Comate
alone with the `.agents` path beside its native one.

### C3. The native project path takes a byte identical copy

The copy at `.comate/skills/recognitio/` stands byte
identical to the canonical skill, pinned by the gate at
`scripts/check_comate.py`, as a real directory of files and
never a symlink. The copy is the whole canonical folder,
scripts and references included, so the native seat holds
the same skill the canonical seat holds and no second
instruction source can grow between them.

Derives from the Microi marketplace page, item
Microi.v8-engine, for the native path, and from canonical
skill, Trust and limits, which keeps one instruction
source for the packet discipline.

### C4. The user scope path is guidance and ships nothing

The user scope path is `~/.comate/skills/recognitio/`,
stated by an implementer as the folder Comate reads for a
user skill. A repository cannot ship a home directory, so
this build places nothing there and states the path here
and in the install section of the README as a copy a user
makes from a pinned checkout. Nothing in the shipped tree
claims the copy exists on any machine.

Derives from the Personal KB marketplace page at
marketplace.visualstudio.com, item Rebekah.personal-kb,
read in full on 2026-10-30, which writes exactly that path
for Comate and the parallel path under `.claude` for the
home platform.

### C5. The frontmatter ships as it stands

The canonical frontmatter carries fields beyond name and
description for its home platform. Whether Comate ignores
the canonical frontmatter fields beyond name and
description, rejects the file, or misreads them stays
unverified, and this build ships no stripped variant,
because a variant adopted before that evidence exists
would fork the skill into two instruction sources. If a
live client shows the fields break the file, the Comate
copies gain a stripped variant whose exact difference the
gate then pins, on the precedent the Qwen bundle records.

Derives from the 4.0 announcement at
comate.baidu.com/zh/news/news/36 for the community protocol
compatibility claim and from docs/qwen-code-brief.md for
the named difference precedent.

### C6. No listing exists and none is claimed

No Comate skill marketplace, skill store, or submission
route is evidenced, and this build ships no submission
pack. Both implementer records install by writing the file
and name no Comate side approval, signing, or listing step,
and the marketplace pages those records stand on are
Microsoft's marketplace for editor extensions, not a
Comate skill listing, so no filing route exists for this
build to prepare.

Derives from the Personal KB marketplace page, item
Rebekah.personal-kb, and the Microi marketplace page, item
Microi.v8-engine, both read in full on 2026-10-30, which
install by placement and name no listing route.

### C7. Invocation and precedence stay unverified

Invocation inside a live Comate session stays unverified.
Whether a skill invoked in Comate gets shell access to run
a bundled script stays unverified. Any Comate side limit
on the length of a SKILL.md file stays unverified. Which
copy a client reads when the skill stands at both project
paths and at the user path stays unverified. The test that
settles all four is one signed in session with a unique
marker in each copy and the invoked path read from the
session itself, run the way the Cursor precedence test was
run, and the client run section below records how far this
box got toward it.

Derives from docs/cursor-plugin-brief.md for the marker
test shape and from canonical skill, Trust and limits,
which keeps every claim scoped to its evidence.

### C8. The trust posture stands unchanged

The trust posture stands unchanged on Comate. The skill
assembles evidence and nothing more, and judgement about
the code belongs to the review skill downstream. No Comate
rule grants the packet merge authority, names a review
model, or approves a red packet.

Derives from canonical skill, Trust and limits, and
canonical skill, The boundary, which keeps judgement with
the review skill downstream. Decision 4 binds this build
like every other build.

## The client run

On 2026-10-30 this lane ran the official client as far as
this box allows. The domain the scoping record could not
resolve through its fetcher answered this lane's shell
requests through the egress proxy, and the download pages
on comate.baidu.com name an official Linux install script
whose full text this lane read before running anything.
The script downloads a tarball named by an installer
record on Baidu's content delivery host. The official
Linux installer record names Comate AI IDE 3.11.5 for
linux x64. The downloaded tarball matched the SHA-256 hash
the installer record publishes, and the installer's own
steps, replicated into a scratch directory with its shell
profile edits skipped, produced a client whose editor
command line reports 3.11.5.

The desktop client opened under a virtual display on this
box with a scratch home, in an empty window. A scratch
project holding the skill at both evidenced project paths
stood prepared beside the run, and the folder argument
did not survive the client's relaunch past the welcome
flow, so the project never stood open as a workspace, and
discovery inside a project is part of what the owed
session must show. The welcome flow was skipped and the
new task surface shows the agent start page. The agent
surface presents a log in button and no task surface
before a sign in, and a license quick login line and a
help documents link stand under the button while the
sidebar carries the same demand as a log in entry at its
foot. No Baidu account or license exists on this box and
no route around the sign in is evidenced. The one missing
piece is a sign in, by Baidu account or by license, that
only the owner can complete.

Everything past that wall stays unverified, and no claim
in this brief rests on a signed in session. The marker
test in rule C7 is the session the record still owes.
